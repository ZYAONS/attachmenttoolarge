Get involved

Contribute, or just come and tell us a story

We don't quiz you on algorithms, we don't check your degree, and we won't ask you to fix three small bugs first to prove you mean it. The only real requirement: when you describe a problem, bring a way to reproduce it.

Why it is worth it

Three things this place gives you

🧩

A small, complete problem domain

The whole field is “the file is too large and the pipe is too narrow”. Clear edges, almost no dependencies, so you can read a module from top to bottom in a single weekend — which in modern open source already counts as a luxury.

📚

Your name ends up in the data

Every limit entry carries a submitter and a verification date. You say 35 MB, and six months later someone re-measures it your way, so your name stays in git blame.

🫶

A place that does not pretend

We accept “I don't know” and “I got it wrong”. So far 11 RFCs have been merged and then overturned by the people who wrote them, and every one is still in the repository.

Contribution flow

Five steps, and the last one is a little unusual

  • STEP 01
    Start with the time you got stuck
    The best starting point for a contribution is a real problem, not “I want to help but I don't know what to do”. Dig out your bounce messages — the material is in there.
  • STEP 02
    Open an issue that says what it means
    Please include: the raw error (plain text or a screenshot), the file size, the provider and product version, the date, and what you already tried. “It doesn't work for me” is not an issue. “It doesn't work for me, here are 12 lines that reproduce it” is.
  • STEP 03
    Fork, and name the branch att/<verb>-<object>
    For example att/add-shard-checksum. Start commit messages with a verb, and let one commit do one thing.
  • STEP 04
    Open a PR — and please keep it under 20 MB
    This is not a joke. We really did reject a 47 MB PR, on the grounds that “the attachment size this site will not accept, this site's own repository will not accept either”. If you must ship a large file, split it with att splitter first, or attach a download link.
  • STEP 05
    Two maintainers review, then it merges
    A rejected PR gets a specific reason, and the branch link stays in the discussion — because “why this doesn't work” is itself part of the documentation.
Code rules

A few hard ones, and not many

  • Comments explain why, not what.
  • Force-pushing to main is banned. It happened to us once, and it was the worst day of 2021.
  • Any change that touches bounce parsing must ship with a real bounce sample (redacted is fine).
  • Wherever a limit number has to match exactly, no hard-coded magic values — read it from the limits data.
  • Naming a file final_final is not allowed. The audit script blocks it, and then reads the file name out loud in CI.
Code of conduct

The one-sentence version

Strict about the work, polite about the person.

Be specific Do not mock questions, do not repost private messages, do not drop someone else's error into the channel as a joke. Technical arguments are settled by evidence, not by who has committed more. Anyone who breaks this is first asked to leave the discussion, then handled by the maintainer group.
And If all you want is to quietly fix one typo, you are very welcome — we have 4,000-odd typos waiting for you, 12 of them on the home page.
